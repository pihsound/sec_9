데이터베이스 보안 개요
★★
데이터베이스 보안 정의

데이터베이스 보안은 데이터베이스에 저장된 데이터에 대한 허가되지 않은 접근·수정·파괴로부터 데이터를 보호하는 것. 데이터베이스 내에 있는 정보에 대한 데이터베이스 관리 시스템(DBMS: Database Management System)의 중요 기능으로써 명확히 정의되어야 한다. 기밀성·무결성·가용성이 모두 포함된다.

데이터베이스는 다양한 응용 프로그램이 공유하는 편리하고 강력한 통로를 통해 상호 연결되고 조직화된 데이터를 손쉽게 접근할 수 있는 특성이 있어요. 이 때문에 한번 침해당하면 대규모 피해가 발생해요. DB 보안의 핵심은 누가(사용자), 어느 부분에(테이블·레코드·필드), 어느 수준에서(읽기·쓰기·삭제) 접근할 수 있는가를 정밀하게 통제하는 것이에요.

CIA 요소DB에서의 의미위협
기밀성 (Confidentiality)부적절한 열람을 방지하고 권한 있는 사용자에게만 공개. 군사적 기밀 같은 중요 정보를 보호하는 것.부적절한 데이터 노출
무결성 (Integrity)부적절한 수정을 방지하고 데이터의 정확성을 보장하는 것.부적절한 데이터 변경
가용성 (Availability)허가된 사용자가 데이터베이스에 접근하는 것을 거부하지 않고 서비스를 지속하는 것.서비스 거부(DoS)

데이터베이스 보안 위협 3종
★★★
위협 유형정의설명
① 부적절한 노출기밀성 침해부적절한 수단으로 우연히 혹은 의도적으로 데이터를 노출함으로써 발생. 인가받지 않은 사용자가 민감 정보를 열람하는 것.
② 부적절한 변경무결성 침해부적절한 데이터 조작으로부터 발생되는 데이터 무결성에 대한 위협. 수정·삭제·삽입 등 불법적 데이터 변경.
③ 서비스 거부가용성 침해서비스를 방해하거나 데이터에 접근하지 못하도록 하는 위협. DoS·DDoS 공격 등.

데이터베이스 정보 출처 유형
★★ 추론통제 이해 기반

데이터베이스에서 정보를 얻을 수 있는 출처는 다음과 같아요. 추론 통제가 필요한 이유를 이해하는 데 핵심이에요.

유형설명예시
정확한 데이터데이터베이스에 직접 저장되어 있는 값직원 이름, 주소, 연봉
통계 (Statistics)급여·계약 금액 같은 수치 데이터에 대한 집계로부터 유용한 정보를 얻음부서 평균 연봉 → 특정 직원 연봉 추론 가능
부정적 결과데이터베이스에 해당 정보가 없다는 사실로부터 정보 추론. 전과 기록이 없으면 전과 없음을 알 수 있음.특정인의 전과 기록 조회 → 없으면 무죄 추론
존재 여부특정 레코드의 존재 여부 자체가 중요한 정보가 될 수 있음특정 인물의 의료 기록 존재 여부
가능한 값다른 4가지 의의 정보로부터 특정한 값을 추론다른 데이터 조합으로 민감 정보 복원

데이터베이스 보안 요구사항 8종
★★★ 2015 지방직 출제

데이터베이스 보안의 요구사항은 8가지로 분류돼요. 시험에서는 "데이터베이스 보안 요구사항이 아닌 것은?"으로 출제돼요. "기밀 데이터 관리 보호"는 요구사항이 아니고, "추론 방지"가 요구사항이에요.

요구사항설명
① 부적절한 접근 방지부적절한 접근으로부터 데이터를 보호하기 위해 접근 통제를 수행해야 함. 사용자 혹은 응용 프로그램의 접근 권한은 DBMS에 의해 통제되어야 함.
② 추론 방지통계 등 일반적인 데이터로부터 비밀 정보를 유추할 수 있는 것을 방지. 데이터 집합으로부터 개별적인 데이터에 대한 추론을 하지 못하도록 하는 통계 제어 등의 방법.
③ 무결성 보장수정권한이 없는 사용자가 수정할 수 있는 되지 않은 접근, 시스템 오류·고장·파업으로부터 데이터를 보호해야 함. 적절한 시스템 통제·백업·복구 절차를 통해 DBMS가 수행.
④ 운영 무결성 보장병행 처리 동안 데이터베이스 내의 데이터에 대한 논리적 일관성을 유지해야 함. 병행 수행 제어 관리자에 의해 보장. 직렬화(Serializability) 보장.
⑤ 의미적 무결성 보장무결성 제약 조건(Integrity Constraints)에 대한 허용 범위 내로써 변경되어야 함.
⑥ 감사 기능다양한 응용 프로그램에서 데이터에 대한 모든 감사(Audit)가 이루어져야 함. 처리하는 데 부하를 주며, 데이터베이스 보안에 대한 책임 추적성 제공.
⑦ 사용자 인증DBMS의 사용자 인증에서 하는 사용자 인증보다 더욱 엄격해야 함. DBMS 사용자는 각종 위협으로부터 신뢰를 보장받아야 하므로 강력한 인증 수행.
⑧ 비밀 관리 및 보호절대로 공개되어서는 안 되는 비밀 데이터가 있을 수 있음. 비밀 데이터를 가지고 있는 객체에 대한 접근을 암호화로 비밀을 보호하고, 권한 있는 자에 대해서만 접근 허용. 비밀 데이터 대한 운영은 감사를 받아야 하지만, 이 감사 역시 통제되어야 함.
⚠함정 ★★★ — 요구사항에 없는 항목 (2015 지방직 출제)
"데이터베이스 보안 요구사항이 아닌 것은? → ③ 추론 보장" → ✗ 출제 함정

실제 요구사항 = 추론 방지(추론을 방지). "추론 보장"처럼 부정확한 표현으로 오답을 유도. "기밀 데이터 관리 보호"는 요구사항 목록에 없음. 8가지: 부적절한 접근 방지·추론 방지·무결성 보장·운영 무결성·의미적 무결성·감사 기능·사용자 인증·비밀 관리.

무결성 보호 — 내부 일관성·외부 일관성
★★
유형설명
내부 일관성
(Internal Consistency)		데이터베이스에 저장되어 있는 데이터의 내부 상태가 일관성을 유지하여야 함.
외부 일관성
(External Consistency)		데이터베이스가 현실 세계를 정확히 반영해야 함. 데이터베이스 관리 시스템이 특정 필드에 잘못된 값이 입력되지 않도록 보장.

2단계 잠금 규약 (2PL: Two-Phase Locking Protocol)
★★★ 운영 무결성 보장 핵심 기법
2단계 잠금 규약 정의

2PL은 병행 처리(동시성 제어)에서 직렬화(Serializability)를 보장하기 위한 잠금 규약. 트랜잭션이 lock과 unlock을 확장 단계 → 수축 단계의 2단계로 구분하여 수행. 병행 수행 제어 관리자가 직렬화를 보장하기 위해 사용. 교재의 "락킹(Locking): 공유 가능한 자원에 대한 접근을 상호 배타적으로 병행 수행을 제어하여 데이터 논리적 일관성을 보장"이 이를 의미함.

2단계 잠금 규약 — 확장 단계 → 수축 단계
구분단계명허용금지
1단계확장(Growing) 단계Lock 획득만 가능Unlock 불가
2단계수축(Shrinking) 단계Unlock만 가능새로운 Lock 획득 불가

핵심 규칙: Lock을 하나라도 해제(Unlock)하면 그 이후에는 새로운 Lock을 절대 획득할 수 없다. 이 규칙을 지키면 트랜잭션의 직렬 실행과 동등한 결과를 보장해요.

2PL이 보장하는 것2PL이 보장 못하는 것
직렬 가능성 (Serializability)
병행 트랜잭션의 결과가 어떤 직렬 실행 결과와 동일함을 보장.		 교착 상태 (Deadlock)
두 트랜잭션이 서로 상대방이 가진 Lock을 기다리는 교착 상태는 방지하지 못함.
⚠함정 ★★★ — 2PL과 Deadlock
"2단계 잠금 규약은 교착 상태(Deadlock)를 방지한다" → ✗ 오답

2PL은 직렬 가능성만 보장. Deadlock은 별도의 방지 기법(타임아웃, 대기 그래프 등)이 필요. 시험에서 "2PL = Deadlock 방지"로 오답 유도가 자주 나와요.

2PL 규약 위반 예시: T1이 Lock(A) → Unlock(A) → Lock(B) 순으로 실행 → Unlock 후 새 Lock 획득 = 위반
2PL 규약 준수 예시: T1이 Lock(A) → Lock(B) → Unlock(A) → Unlock(B) → 정상

데이터베이스 보안 통제 3종 개요
★★★ 매년 출제

데이터베이스 보안 통제는 접근 통제·흐름 통제·추론 통제 세 가지로 구성돼요. 각각의 목적과 대상이 명확히 다르므로 정확히 구분해야 해요.

접근 통제
(Access Control)
목적: 인증된 사용자에게 허가된 범위 내에서만 DB 접근 허용.
대상: 데이터베이스 시스템 자체에 대한 접근.
방법: 사용자가 DB 접근 시 접근 권한(Access Right)을 확인하여 허용 여부 결정.
기술: 기본 릴레이션 통제, 뷰(View)를 통한 접근 제한, 암호화.
흐름 통제
(Flow Control)
목적: 접근 가능한 객체 간의 정보 흐름을 통제하는 것.
핵심: 높은 보안 등급에서 낮은 보안 등급으로 객체 전달이 발생 시, 정보가 에서 유출되지 않도록 조정.
낮은 보호 수준의 객체로 이동된다면, 접근 권한이 없는 객체에서도 접근할 수 있기 때문에 보안이 침해됨.
예: 기밀 문서(높은 등급) → 일반 문서(낮은 등급)으로 복사 금지.
추론 통제
(Inference Control)
목적: 간접적인 데이터 노출로부터 데이터를 보호하기 위한 것.
핵심: 직접 접근 권한은 없지만 공개된 데이터로부터 비밀 정보를 추론하는 것을 방지.
해결 방법: ① 비밀 데이터의 암호화 ② 데이터 추적 ③ 데이터 위장.
예: 평균 연봉 통계로 특정인 연봉 추론 방지.
구분접근 통제흐름 통제추론 통제
통제 대상DB 시스템 자체 접근객체 간 정보의 흐름 방향합법적 접근에서의 간접 추론
위협인가받지 않은 사용자의 접근높은 등급 → 낮은 등급으로 정보 유출통계·공개 데이터로 기밀 추론
핵심 키워드권한(Right), GRANT, 뷰(View)높은→낮은 등급 흐름 차단간접 접근, 상호 연관, 누락 데이터
해결 기술DBMS 접근 권한, 뷰, 암호화정보 흐름 정책 수립암호화, 데이터 추적, 데이터 위장
⚠함정 ★★★ — 흐름 통제 방향 혼동 (2020 경찰간부 출제)
"흐름 통제: 낮은 보안 등급에서 높은 보안 등급으로 정보 흐름 발생 시 기밀성이 위반되지 않도록 통제하는 것이다" → ✗ 오답

흐름 통제는 높은 보안 등급에서 낮은 보안 등급으로 흐르는 것을 통제. 낮은 등급→높은 등급으로 흐르면 기밀성 문제가 아니에요. 기밀 정보(높은 등급)가 낮은 등급으로 흘러나가는 것이 위험이에요.

"낮은 비밀 취급 등급자가 레코드 입력 시, 오류를 통하여 자신보다 높은 비밀 취급 등급자가 있다는 사실을 알게 되는 사례" → 추론 통제

이는 존재 여부(Existence)를 통한 추론. 직접 접근은 못하지만 오류 메시지로 간접적으로 정보를 얻는 것 = 추론 통제 대상.

추론 통제 — 추론 채널 3종
★★★
추론 통제 개요

추론 통제는 데이터로부터 비밀을 추론하기 위한 통제. 시스템 내의 주요 추론 채널은 3가지로 분류됨. 접근 권한이 없는 사용자가 정당한 접근을 통해 DBMS에 들어오더라도 허가받지 않은 정보를 추론하지 못하도록 하기 위한 규칙.

1
간접 접근 (Indirect Access)
접근 권한이 없는 데이터 X에 대한 접근 권한을 갖는 데이터 Y를 통하여 데이터 X에 접근하지 않은 데이터를 알 수 있을 때 간접 접근에 의한 추론이 발생함. 허가된 경로를 통해 허가되지 않은 정보를 간접 추론.
2
상호 연관 데이터 (Correlated Data)
데이터 Y가 접근하지 않은 데이터 X와 상호 연관되어 있을 때 상호 연관 데이터(Correlated Data)가 전형적인 추론 채널이 됨. 데이터 Y에 대한 접근은 X를 얻음으로써 얻을 수 있음. 예: 평균 연봉 통계로 특정인 연봉 추론.
3
누락 데이터 (Missing Data)
시스템이 알려주지 않더라도, 알려주는 것을 통하여 누락(Missing) 데이터에 의한 추론이 발생함. 데이터가 없어도 데이터의 부재 자체로도 정보를 추론할 수 있다면, 이러한 추론을 통하여 비밀을 알 수 있음. 예: 특정 레코드가 없다는 사실로 존재 여부 확인.

1
SQL 보안 모델 개요
★★★

SQL 보안 모델에서 사용자는 객체에 대한 행위를 호출하며, DBMS는 사용자가 요청한 행위를 허용할 것인지를 결정해야 함. 객체가 생성될 때 이를 생성한 사용자가 소유자(Owner)가 되며 초기에는 소유자만이 객체에 대한 접근 권한을 가짐. 다른 사용자들은 특권(Privilege)을 이용하여 접근 권한을 부여받아야 함.

2
GRANT — 권한 부여
★★★

SQL에서 특권(Privilege)은 GRANT 및 REVOKE 오퍼레이션을 이용하여 관리됨. 특권은 특정한 행위를 지칭하며, 테이블의 특정한 애트리뷰트(컬럼)에도 제한될 수 있음.

-- a와 b에게 테이블 Diary의 Day열과 Flight열에 대한 검색·수정 권한을 부여
GRANT SELECT, UPDATE (Day, Flight)
ON TABLE Diary
TO a, b;

-- WITH GRANT OPTION: a가 다른 사용자에게도 재부여 가능
GRANT SELECT
ON TABLE Diary
TO a
WITH GRANT OPTION;
WITH GRANT OPTION 주의: Diary가 삭제되면 a가 부여했던 다른 사용자에게 부여된 권한 모두가 연쇄적으로 취소(CASCADE)되어야 함. 이를 위해 필요한 정보를 데이터베이스가 유지하여야 함.
3
REVOKE — 권한 취소
★★★
-- a로부터 테이블 Diary에 대한 수정 권한을 취소
REVOKE UPDATE
ON TABLE Diary
FROM a;
SQL 권한 명령어기능사용 주체
GRANT다른 사용자에게 권한 부여. DBA 또는 소유자가 사용.DBA, 객체 소유자
REVOKE부여된 권한 취소. DBA 또는 소유자가 사용.DBA, 객체 소유자
DENY특정 사용자의 권한을 명시적으로 거부. (SQL Server 등 일부 DBMS)DBA
DROP테이블·뷰 등 객체 자체를 삭제하는 DDL 명령. 권한 관리 명령이 아님.소유자
⚠함정 ★★★ — DROP은 권한 관리 명령어가 아님 (2017 서울시 출제)
"데이터베이스 관리자(DBA)가 부여할 수 있는 SQL 기반 접근 권한 관리 명령어로 옳지 않은 것은? → DROP" → ✓ 정답 (DROP이 오답)

DBA의 접근 권한 관리 명령어: GRANT(부여)·REVOKE(취소)·DENY(거부). DROP은 테이블/뷰 등 객체를 삭제하는 DDL(Data Definition Language) 명령어로 접근 권한 관리와 관계없음.

4
뷰(View) — 접근 통제 수단
★★★
뷰(View) 정의

뷰(View) 또는 스냅샷(Snapshot)은 기본 릴레이션의 항목으로 정의되는 유도 릴레이션(Derived Relation). 따라서 자신의 고유한 저장 데이터를 갖지 않음. 전체 권한 받은 사용자만 볼 수 있도록 한정하는 데 사용됨.

-- Status가 'business'인 레코드만 보여주는 뷰 생성
CREATE VIEW Business_trips AS
SELECT * FROM Diary
WHERE Status = 'business'
WITH CHECK OPTION;
뷰의 보안 특성설명
논리적 독립성데이터의 논리적 독립성을 제공하며, 응용 프로그램과 가까운 표현으로 접근 권한이 있도록 함.
통제된 호출통제된 호출(Controlled Invocation)을 구현할 수 있음.
보안 필터보안 필터(Secure Filter) 역할로 접근을 제한하여 민감 데이터를 숨길 수 있음.
접근 제한접근 범위를 좁혀 특정 컬럼·행만 볼 수 있도록 제한.
저장 데이터 없음뷰는 기본 테이블로부터 유도된 가상 테이블이므로 자신의 고유 저장 데이터를 갖지 않음.
구분기본 릴레이션 (Base Relation)뷰 (View)

데이터베이스 암호화 4방식
★★★ 2021 군무원·2022 국가직·경찰간부 출제

DB 암호화 방식은 암호화 모듈이 어디에 설치되느냐에 따라 4가지로 구분돼요. 시험에서는 각 방식의 설치 위치, 애플리케이션 수정 여부가 핵심 구분 기준이에요.

Plugin 방식
(암·복호화 모듈 → DB 서버)
설치 위치: DB 서버 내에 암·복호화 모듈 설치.
동작: DB 서버 내부에서 암·복호화 처리.
APP 수정: ⚠ 구축 시 일부 애플리케이션 수정 필요할 수 있음.
DB 성능: DB 서버에 대한 성능 검토 필요.
특징: DB 서버의 처리 부하 증가 가능. API 방식에 비해 DB 성능 영향.
API 방식
(암·복호화 모듈 → 응용 서버)
설치 위치: 응용 프로그램 서버에 암·복호화 모듈 설치.
동작: 응용 서버에서 암·복호화 처리 후 DB에 저장.
APP 수정: ⚠ 애플리케이션 수정 필요.
DB 성능: DB 서버에는 직접 영향 없음.
특징: 애플리케이션 레벨에서 암호화 처리. 개발 변경 비용 발생.
Hybrid 방식
(DB 서버 + 응용 서버 조합)
설치 위치: DB 서버와 응용 서버 모두 활용.
구성: Plug-In 방식과 API 방식이 결합된 형식.
APP 수정: ✓ 일반적으로 애플리케이션 수정 필요 없음.
특징: Plug-In의 배치 업무 성능 저하를 API 방식으로 보완. 두 방식의 장점 결합.
TDE 방식
(Transparent Data Encryption)
설치 위치: DBMS 내부 또는 옵션으로 제공.
동작: DBMS에 내장 또는 옵션으로 제공되는 암호화 기능을 이용. DB 내부에서 암·복호화 처리.
APP 수정: ✓ 일반적으로 애플리케이션 수정 필요 없음.
주의: DBMS의 TDE 지원 가능 여부 확인 필요. 아카이브 하이버네이션 필요할 수 있음.
방식암호화 위치형태APP 수정특징

📄 2020 경찰간부 · 흐름 통제 방향 오답★★★
데이터베이스 보안 통제에 대한 설명 중 가장 옳지 않은 것은?
① 흐름통제: 접근 가능한 객체 간의 정보 흐름을 통제하는 것으로, 낮은 보안 등급에서 높은 보안 등급으로 정보 흐름 발생 시 기밀성이 위반되지 않도록 통제하는 것이다.
② 추론통제: 간접적인 데이터 노출로부터 데이터를 보호하는 것으로, 비밀 정보의 은폐·데이터 위장 등의 방법으로 통제할 수 있다.
③ 접근통제: 인증된 사용자에게 허가된 범위 내에서만 접근을 허용하여 내부 정보에 대한 접근을 통제하는 것이다.
④ 뷰(View): 기본 테이블로부터 유도되어 만들어지는 가상 테이블로, 데이터의 논리적 독립성을 제공한다.
정답 ① — 흐름 통제는 높은 보안 등급에서 낮은 보안 등급으로 정보가 흘러나가는 것을 통제. "낮은 → 높은"이 틀림. 기밀 정보가 낮은 등급으로 유출되는 것이 위험이므로 이를 막는 것이 흐름 통제.

① TDE 방식
② API 방식
③ Plug-In 방식
④ Hybrid 방식
정답 ① — 키워드: "DBMS에 내장 또는 옵션" + "응용 프로그램 수정 없음" + "DB 내부에서 처리" = TDE(Transparent Data Encryption). API는 응용 서버에 설치·수정 필요. Plug-In은 DB 서버 내 설치·일부 수정 가능. Hybrid = Plugin+API 결합.

① Plug-In 방식은 구축 시 일부 응용프로그램 수정이 필요할 수 있으며 DB 성능에 대한 검토가 필요하다.
② Hybrid 방식은 일반적으로 Plug-In 방식과 TDE(Transparent Data Encryption) 방식이 조합된 것이다.
③ API 방식은 응용프로그램 서버에 설치하는 방식으로써 응용프로그램의 수정이 필요하다.
④ TDE 방식은 DBMS 내부 또는 옵션으로 제공되는 암호화 기능을 이용한다.
정답 ② — Hybrid = Plug-In 방식 + API 방식의 결합. TDE와 조합이 아님. ①③④는 모두 정확한 설명.
📄 2022 경찰간부 · Hybrid = Plugin+API, 파일 암호화 방식 오답★★★
데이터베이스 암호화 방법의 내용으로 가장 적절하지 않은 것은?
① Hybrid 방식은 Plug-In 방식의 단점인 배치 업무의 성능 저하를 보완하기 위해 API 방식을 이용하는 구성이다.
② Plug-In 방식은 암 복호화 모듈을 DB 서버 내에 설치하고 이곳에서 암 복호화를 수행하는 구조이다.
③ API 방식은 암 복호화 모듈을 애플리케이션 서버 내에 설치하고 이곳에서 암 복호화를 수행하는 구조로 애플리케이션의 수정을 동반한다.
④ 파일 암호화 방식은 DBMS에 추가 기능으로 제공되는 암호화 기능을 이용하여 DB 내부에서 데이터 파일 저장 시 암호화한다.
정답 ④ — "DBMS에 추가 기능으로 제공되는 암호화 기능 + DB 내부에서 암호화" = TDE 방식. "파일 암호화 방식"이라는 명칭은 잘못됨. ①Hybrid=Plugin+API ✓ ②Plug-In=DB서버 ✓ ③API=응용서버+수정 ✓.
📄 단원별 연습 문제 · DB 보안 10번 · 추론 통제 설명★★
데이터베이스 보안으로 옳지 않은 것은?
① 허가된 사용자에게만 접근 권한을 부여하고, 접근 권한은 DBMS에 의해 통제되어야 한다.
② 데이터 집합으로부터 개별적인 데이터에 대한 추론을 할 수 있도록 한다.
③ 모든 데이터에 대한 모든 감사가 이루어져야 한다.
④ 일관성을 위해 모든 트랜잭션(Transaction)으로 실행되어야 한다.
정답 ② — DB 보안 요구사항은 추론 방지. 데이터 집합으로부터 개별 데이터를 추론할 수 없도록 해야 함. "할 수 있도록 한다"는 정반대.
📄 단원별 연습 문제 · DB 보안 통제 11번 · 추론 통제 정의★★★
데이터베이스 보안 제어 어(Inference Control)에 대한 설명으로 옳은 것은?
① 데이터 집합으로부터 개별적인 데이터에 대한 추론을 할 수 없도록 한다.
② 시스템에 대한 모든 직접적 보호에서 세운 코드(Mode)에 따라 엄격하게 한다.
③ 설정된 낮은 보호 등급을 가진 것을 사 한다.
④ 발생할 수 있는 허가되지 않은 접근을 제한한다.
정답 ① — 추론 통제(Inference Control) = 데이터 집합으로부터 개별 데이터에 대한 추론을 할 수 없도록 하는 것. ④는 접근 통제의 설명. 추론 통제 = ①, 접근 통제 = ④.
📄 2025 국회직 9급 · SQL 인젝션 관련 SQL 쿼리★★★
다음 SQL 쿼리문에 대한 설명으로 옳지 않은 것은?
SELECT * FROM user WHERE name = '' or '=';
① SQL 인젝션 공격에 취약한 문장이다.
② WHERE절에서 user의 모든 레코드를 반환받을 가능성이 있다.
③ 위 SQL 쿼리문의 취약점 해결 방법으로 prepared statements를 사용하는 것이 좋다.
④ 입력값 검증을 위하여 블랙리스트 방식으로 유효한 값만 허용하는 것이 좋다.
정답 ④ — SQL 인젝션 방어에는 화이트리스트(허용 목록) 방식이 적합. 블랙리스트(차단 목록)는 알려진 공격 패턴만 막아 우회 가능. '' or '='는 항상 참이 되어 모든 레코드 반환 → SQL Injection 공격 패턴.
🗄 데이터베이스 보안 전체 핵심 암기
DB 보안 3대 위협부적절한 노출(기밀성) / 부적절한 변경(무결성) / 서비스 거부(가용성)
보안 요구사항 ≠"기밀 데이터 관리 보호" = 요구사항에 없음. "추론 방지"는 요구사항 맞음.
접근 통제사용자 접근 권한 확인. GRANT·REVOKE·VIEW. 인증된 사용자에게만 허용.
흐름 통제높은→낮은 등급 정보 흐름 차단. (낮은→높은 아님!)
추론 통제공개 데이터로 기밀 추론 방지. 채널 3종: 간접 접근·상호 연관·누락 데이터.
GRANT·REVOKE권한 부여·취소. DROP은 권한 관리 아님(DDL·객체 삭제).
뷰(View)유도 릴레이션. 고유 저장 데이터 없음. 보안 필터·논리적 독립성 제공.

  • "흐름 통제 = 낮은 등급 → 높은 등급으로 흐름 차단" → ✗ (높은→낮은 흐름 차단)
  • "기밀 데이터 관리 보호 = DB 보안 요구사항" → ✗ (요구사항 목록에 없음)
  • "Hybrid = Plugin + TDE 조합" → ✗ (Hybrid = Plugin + API 조합)
  • "DROP = DBA 접근 권한 관리 명령어" → ✗ (DROP은 DDL·객체 삭제)
  • "뷰는 자신의 고유 저장 데이터를 가짐" → ✗ (유도 릴레이션, 저장 데이터 없음)
